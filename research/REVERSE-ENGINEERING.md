# Реверс оригинального Control Center для G6 MF

Дата: 31 октября 2026. Пакет GIGABYTE **ControlCenter 3.0 Package v6.045**. Устройство: **G6 MF / BIOS FB10**.

Последующее обновление: создано собственное приложение 0.1, проверены запись кривой, максимальное охлаждение и зарядный порог с восстановлением исходного состояния. Ниже — исходный отчёт реверса; актуальные результаты интеграции находятся в `../docs/VALIDATION.md`.

## Результат

1. Официальный ZIP скачан и проверен по размеру/локально рассчитанному SHA256. InstallShield CAB извлечены **без запуска установщика**: 215 файлов, Unshield завершился успешно.
2. Извлечены девять основных AppX-пакетов x64, без регистрации или установки в Windows.
3. Декомпилированы девять основных .NET-модулей: **273 C#-файла**, все девять запусков ILSpy завершились с кодом 0 и пустыми журналами. Дополнительно восстановлен установленный CClnk.exe.
4. Разобраны нативные экспорты установленной InsydeDCHU.dll, расширенный вызов DLL FnKey и диспетчер IOCTL установленного AcpiBridge.sys. Сохранены дизассемблированные функции.
5. Написана собственная диагностика только чтения; получены реальные данные двух вентиляторов и признаки возможностей через установленный драйвер.
6. Составлены `api-map.json` и `api-call-index.json`: форматы нужных команд и 994 строки вызовов/объявлений из восстановленных модулей со ссылками на файлы и номера строк. Текстовый индекс не является полным графом вызовов.

Это восстановленный код из бинарников, а не оригинальный исходный репозиторий производителя. Полная реконструкция C/C++ нативных модулей и прошивки не выполнялась. Декомпилированные проекты не проверялись сборкой; их назначение здесь — исследование протокола.

## Реальная цепочка взаимодействия

```text
Наш код
  → функции InsydeDCHU.dll
  → интерфейс устройства {86994c74-ad43-4812-b7e7-0c420b5c5fd7}
  → штатный подписанный AcpiBridge.sys
  → ACPI _DSM / прошивка
```

`CClnk.exe` — только запускатель FnKey через `shell:appsFolder`, а не аппаратный контроллер. Его версия 7.32.0.0 не является версией основного пакета 6.045.

Названия `GetWMI`/`SetWMI` в OEM-коде вводят в заблуждение: в изученных современных модулях они оборачивают функции DCHU, а не обязательно Windows WMI. Для нового приложения не требуется создавать отсутствующие `GB_WMIACPI_*`.

Подтверждено совпадение **обоих** базовых компонентов пакета с установленными:

- DCHU DLL: `470d96cae14fef2823330c63ea683cf87cb0f6984dc4eb86d21420ff71be3299`.
- AcpiBridge.sys: `be879af2ef1beaa3ad041c30abd103c5e9e872d23ea8442b57682bb0d06ea153`.

## Нативная DLL и драйвер

У установленной DLL пять экспортов: `GetDCHU_Data_Buffer`, `GetDCHU_Data_Integer`, `ReadAppSettings`, `SetDCHU_Data`, `WriteAppSettings`.

DLL перечисляет интерфейс устройства, открывает его через `CreateFileW` с доступом read/write и общим доступом read/write. Даже аппаратные чтения поэтому могут требовать повышенных прав: в ограниченном процессе первое чтение вернуло 0; в процессе с нужным доступом чтение успешно.

| IOCTL | Найденный обработчик драйвера, VA | Назначение |
|---|---|---|
| `0x322400` | `0x140006560` | Оценка ACPI/DSM, аппаратные запросы |
| `0x322404` | `0x14000687c` | Ожидание события; подтверждается кодом DCHUService |
| `0x322408` | `0x14000670c` | Получение значения уведомления |
| `0x32240c` | `0x140006a4c` | Общее хранилище AppSettings |

Диспетчер установленного драйвера расположен по VA `0x140007880`; он вычитает `0x322400` и выбирает четыре ветки с шагом 4. Адреса применимы только к указанному хешу драйвера. Функции сохранены в `native/AcpiBridge-dispatch-and-evaluate.asm`.

В DLL у основных DSM-вызовов видны UUID `93f224e4-fbdc-4bbf-add6-db71bdc0afad`, имя `_DSM`, номер команды и буферы аргументов. Для изученной DLL в `DeviceIoControl` передаются входной размер `0x420` и выходной `0x40c`; это установлено по x64 ABI в дизассемблере, а не по чужой документации.

Различия возвратов важны для новой обёртки:

- `GetDCHU_Data_Integer`: возвращает само значение и записывает его по выходному указателю. **Не возвращает номер команды.** Ноль сам по себе не позволяет отличить валидный ноль от ошибки: нужен контроль изменения выходного значения.
- `GetDCHU_Data_Buffer`: на удачном пути возвращает номер команды. У копирования буферного элемента обнаружен дополнительный байт после основного цикла; нельзя выделять ровно 256 байт под ожидаемый 256-байтный ответ.
- `ReadAppSettings`: на удачном пути возвращает **4096**, даже если запрошен 1 или 256 байт. Это не число скопированных байт.
- Использованная диагностика выделяет 4096 байт под выходные данные и вызывает всё последовательно.

У DLL из AppX FnKey другой хеш: `dab807b5d4a621893ef5c5c1941e9d8ce91dda6b2518e931f4bb4727dfd80e98`. Она дополнительно экспортирует `SetDCHU_DataEx`. Его функция по RVA `0x2ae0` также использует IOCTL `0x322400` и копирует выходной ACPI-буфер. У DLL FanSpeedSetting ещё другой хеш: `cb3b03f38d4f3b98709a2e395acec0e958841e67627855874268e418b990f106`.

Вывод: нельзя искать DLL только по имени или подменять системную копию. Для новой программы нужно явно выбрать и проверить нужную версию по хешу/экспортам. Системные копии не заменялись.

## Охлаждение

### Телеметрия — подтверждена чтением

`GetDCHU_Data_Buffer(12, output)`:

| Данные | CPU | GPU 1 | GPU 2, если есть |
|---|---:|---:|---:|
| Период тахометра, uint16 BE | 2–3 | 4–5 | 6–7 |
| Управление вентилятором, raw 0–255 | 16 | 19 | 22 |
| Сырая температура | 18 | 21 | 24 |

RPM в оригинальном интерфейсе вычисляется как `round(120 / (5.565217391304348e-5 * period))`; при нулевом периоде отображается 0. Поле, названное `rpm` внутри OEM-кода, на промежуточном этапе содержит период, а не готовые обороты. Процент raw/255 не всегда совпадает с процентом на экране: оригинал учитывает TurboFan_MaxDuty.

Для CPU в OEM-коде есть калибровка температуры по строке TDP. Наш снимок специально хранит сырую температуру и не выдаёт её за независимо проверенный датчик CPU package.

`GetDCHU_Data_Buffer(13, output)` содержит число вентиляторов в байте 12; оригинал допускает пользовательскую кривую при `count > 1 && (byte43 & 2) == 0`.

На G6 MF получено: **2 вентилятора, byte43 = 1, проверка поддержки custom проходит**. Это подтверждение признака возможности, а не успешной записи кривой.

### Режимы и кривые — восстановлены статически

- Режим: `SetDCHU_Data(121, [value,0,0,1],4)`; 0 = автомат, 1 = максимум, 6 = custom. Другие режимы требуют соответствующих признаков поддержки.
- Затем оригинал сохраняет режим в AppSettings, страница 4 / смещение 5 / длина 1.
- FanOffset: та же команда 121, подкоманда в старшем байте = 14; значение `round(percent/100*255)`. Сохранение: 4 / 7 / 1.
- Кривая старого формата: пакет 14 длиной 256 байт; CPU T2/D2/T3/D3 в байтах 2–5, GPU1 в 6–9, GPU2 в 10–13. Duty кодируется 0–255.
- Далее в пакете записываются коэффициенты R12/R23/R34 как uint16 BE. Формула оригинала: `round((Dnext-Dprev)/(Tnext-Tprev)*2.55*16)`, где D задан в процентах. Требуются строго разнесённые температуры, допустимые пределы и правильные крайние точки.
- Значения сохранённых настроек кривой имеют отдельную раскладку и местами другой порядок байт; их нельзя смешивать с аппаратным пакетом 14.
- В FnKey найден новый формат таблиц с десятью уровнями и разными порогами повышения/снижения оборотов. Пакет 4 через Ex: подкоманды 40/41 = читать/записать CPU+GPU, 42/43 = каналы 3+4. Поддержка этого варианта на G6 MF ещё не проверялась.

Полный формат и исходные методы отмечены в `api-map.json`. Ни одна из описанных команд записи не выполнялась.

## Питание от АКБ и сети

В `FnKey/Features.cs:SetPowerMode` найдены значения: **0 quiet, 1 powerSaving, 2 performance, 3 entertainment**.

OEM сначала сохраняет AppSettings 1 / 1 / 1, затем отправляет команду **121**, подкоманду **25** в старшем байте четырёхбайтного аргумента. В performance могут добавляться флаги `0x80` и `0x40` по проверкам DTT и TurboFan. Полное переключение в `FnKey/Form1.cs:OnChangePowerMode` также обрабатывает EnergyStar, GPU-настройки, лимиты и вентиляторы по признакам поддержки.

Поэтому будущая кнопка профиля должна выполнять согласованную последовательность для G6 MF, а не единственный произвольный вызов. Также нужно различать сохранённый выбранный режим и фактические аппаратные настройки.

В коде есть обработка смены AC/DC, восстановления после сна и отдельного режима от батареи. Мы можем реализовать свою логику этих событий, используя восстановленные аппаратные команды.

## Батарея

В `ControlCenter30/Window1.cs` найден интерфейс FlexiCharger:

- Чтение: `SetDCHU_DataEx(4, input,256,output)`, `input[0]=30`.
- Ответ: 0 = включение, 1 = порог старта, 2 = порог остановки; 16–31 и 32–47 содержат предлагаемые прошивкой допустимые пороги.
- Запись: тот же Ex, `input[0]=31`, байты 1/2/3 = включение/старт/стоп.

Это хороший кандидат для будущего ограничения заряда, но **поддержка на нашем G6 MF ещё не проверена**. Вызов с названием Set может быть запросом чтения по содержимому пакета; наша текущая диагностика такие запросы намеренно не использует.

Кроме того, найден отдельный механизм EnergySave в FnKey с порогами из пакета 17 (байты 208/209). Его нельзя автоматически считать тем же механизмом зарядного окна FlexiCharger.

## Реальная проверка на G6 MF

Скрипт `tools/Read-G6Snapshot.ps1`:

- Проверяет модель и точный SHA256 установленной DLL.
- Содержит только P/Invoke для двух getter-функций и ReadAppSettings; setter-функций в нём нет.
- Читает пакеты 12/13, страницы AppSettings 1/4/7 и четыре целочисленных запроса, найденных в оригинальной проверке возможностей.
- Сохраняет исходные данные и декодирование. Не запускает штатные службы и не изменяет профили.

Полученные целочисленные признаки:

| Команда | Ответ |
|---|---|
| 16 | `0x00000893` |
| 70 | `0x00002100` |
| 96 | `0x0000021c` |
| 122 | `0x70020053` |

Страница 7 начинается с версии 0, поэтому применим старый путь проверки возможностей из OEM-кода. В ответе команды 16 включены биты штатных PowerMode, RGB-клавиатуры и FanSetting; биты UI CPUOC/GPUOC не включены. Это не доказательство невозможности любых способов изменения CPU/GPU, но достаточное основание не обещать штатный разгон/undervolt на этом ноутбуке.

Зафиксированы правдоподобные периоды тахометров и примерно 2300–2400 RPM по оригинальной формуле; независимого сравнения с физическим тахометром/HWiNFO не выполнялось. Температуры менялись между снимками; это не нагрузочный тест и не оценка качества охлаждения.

## Что уже можно использовать для собственного приложения

Есть основа для реальной телеметрии через штатный драйвер, декодирования вентиляторов и определения возможностей, а также восстановленные последовательности аппаратных команд для профилей и охлаждения.

Следующий этап — собственный аппаратный адаптер с явным выбором DLL и отдельным режимом записи, затем поочерёдная проверка «автомат/максимум/возврат», режимов питания и пользовательской кривой с чтением результата. Ограничение заряда и расширенные таблицы пока остаются кандидатами, а не подтверждёнными функциями G6 MF.
